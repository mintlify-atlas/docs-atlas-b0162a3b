---
title: Vector Retrieval
description: Configure and use embedding-based semantic search in Membrane
---

Membrane supports optional embedding-based retrieval for competence and plan_graph records when running on Postgres with pgvector.

## Overview

Without embeddings (Tier 1 and Tier 2), Membrane uses confidence-based applicability scoring as a fallback. With embeddings enabled (Tier 3 and Tier 4), retrieval uses cosine similarity between the task descriptor and stored trigger embeddings.

---

## Embedding Configuration

Embeddings require three configuration values:

```yaml config.yaml
backend: postgres
postgres_dsn: "postgres://membrane:membrane@localhost:5432/membrane?sslmode=disable"

embedding_endpoint: "https://api.openai.com/v1/embeddings"
embedding_model: "text-embedding-3-small"
embedding_dimensions: 1536
```

### Environment Variables

Set the API key via environment variable:

```bash
export MEMBRANE_EMBEDDING_API_KEY="sk-..."
```

Or in the config file (not recommended for production):

```yaml
embedding_api_key: "sk-..."
```

### Supported Endpoints

Any OpenAI-compatible embeddings API:

- **OpenAI**: `https://api.openai.com/v1/embeddings`
- **Azure OpenAI**: `https://<resource>.openai.azure.com/openai/deployments/<deployment>/embeddings?api-version=2023-05-15`
- **OpenRouter**: `https://openrouter.ai/api/v1/embeddings`
- **Self-hosted** (e.g., text-embeddings-inference, vLLM)

<Note>
Membrane expects the standard OpenAI response format with `data[0].embedding` as a float32 array.
</Note>

## API Key Authentication

The embedding client (`pkg/embedding/embedding.go`) sends the API key as a Bearer token:

```go
req.Header.Set("Authorization", "Bearer "+c.apiKey)
```

For Azure OpenAI, use the `api-key` header instead (requires code modification or API gateway).

## Embedding Model Selection

### Recommended Models

| Model | Dimensions | Use Case |
|-------|------------|----------|
| `text-embedding-3-small` | 1536 | Default, good balance of cost/quality |
| `text-embedding-3-large` | 3072 | Higher quality, 2x cost |
| `text-embedding-ada-002` | 1536 | Legacy, same cost as 3-small |

### Custom Dimensions

OpenAI's `text-embedding-3-*` models support custom dimensions:

```yaml config.yaml
embedding_model: "text-embedding-3-large"
embedding_dimensions: 1024  # reduced from 3072
```

This saves storage and query time with minimal quality loss.

<Warning>
If you change `embedding_dimensions` after ingesting data, you'll get a metadata mismatch error. Start fresh or re-embed all records.
</Warning>

## How Embeddings Are Generated

### During Ingestion

When you ingest a competence or plan_graph record, Membrane:

1. Extracts the `trigger` field from the payload
2. Calls the embedding endpoint with the trigger text
3. Stores the embedding in the `trigger_embeddings` table
4. Associates the embedding with the record ID

### Example Flow

<CodeGroup>
```go Go
req := ingestion.IngestCompetenceRequest{
    Source:  "agent",
    Trigger: "fix linker cache error in Go builds",
    Procedure: schema.Procedure{
        Steps: []schema.Step{
            {Action: "run", Args: map[string]any{"command": "go clean -cache"}},
            {Action: "run", Args: map[string]any{"command": "go build"}},
        },
    },
}

rec, err := m.IngestCompetence(ctx, req)
// Embedding generated for "fix linker cache error in Go builds"
```

```typescript TypeScript
const record = await client.ingestCompetence({
  source: "agent",
  trigger: "fix linker cache error in Go builds",
  procedure: {
    steps: [
      { action: "run", args: { command: "go clean -cache" } },
      { action: "run", args: { command: "go build" } },
    ],
  },
});
// Embedding generated for "fix linker cache error in Go builds"
```
</CodeGroup>

### Storage Schema

Embeddings are stored in the `trigger_embeddings` table:

```sql
CREATE TABLE trigger_embeddings (
    record_id TEXT PRIMARY KEY REFERENCES memory_records(id) ON DELETE CASCADE,
    embedding vector(1536),  -- dimension from config
    model TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL
);
```

## Similarity Search

Membrane uses **cosine similarity** via pgvector's `<=>` operator.

### Query Example

```sql
SELECT record_id
FROM trigger_embeddings
ORDER BY embedding <=> $1::vector
LIMIT 10;
```

The `SearchByEmbedding` function in `pkg/storage/postgres/postgres.go`:

```go
func (s *PostgresStore) SearchByEmbedding(ctx context.Context, query []float32, limit int) ([]string, error) {
    rows, err := s.db.QueryContext(ctx,
        `SELECT record_id
         FROM trigger_embeddings
         ORDER BY embedding <=> $1::vector
         LIMIT $2`,
        vectorLiteral(query), limit,
    )
    // ...
}
```

### Distance Metrics

Membrane uses **cosine distance** (`vector_cosine_ops`). pgvector also supports:

- **L2 distance** (`vector_l2_ops`): Euclidean distance
- **Inner product** (`vector_ip_ops`): Dot product (for normalized vectors)

To change the metric, modify the index creation in `schema.sql`:

```sql
CREATE INDEX idx_trigger_embeddings_ann
    ON trigger_embeddings USING ivfflat (embedding vector_l2_ops);
```

## Retrieval Behavior

### With Embeddings Enabled

1. **Task descriptor** is embedded into a query vector
2. **Competence and plan_graph records** are scored by cosine similarity
3. **Semantic, episodic, working** records use salience/confidence ranking
4. Results are merged and returned in descending score order

### Fallback (No Embeddings)

1. **Competence and plan_graph records** are scored by confidence alone
2. No vector search is performed
3. Results are returned in descending salience order

<Note>
Semantic and episodic records never use embeddings for retrieval, even when embeddings are enabled. Only competence and plan_graph records benefit from similarity search.
</Note>

## Performance Tuning

### IVFFlat Index Configuration

The default IVFFlat index uses 100 lists:

```sql
CREATE INDEX idx_trigger_embeddings_ann
    ON trigger_embeddings USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);
```

**Tuning `lists`:**

- **Small datasets** (under 10k embeddings): `lists = 100`
- **Medium datasets** (10k-100k): `lists = 500`
- **Large datasets** (over 100k): `lists = 1000` or use HNSW

Rule of thumb: `lists ≈ sqrt(num_embeddings)`

### HNSW Alternative

For large datasets or lower latency, use HNSW:

```sql
DROP INDEX idx_trigger_embeddings_ann;
CREATE INDEX idx_trigger_embeddings_hnsw
    ON trigger_embeddings USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
```

**HNSW parameters:**

- `m`: Number of connections per node (default: 16, range: 4-64)
- `ef_construction`: Build-time search depth (default: 64, higher = better recall, slower build)

Query-time parameter:

```sql
SET hnsw.ef_search = 100;  -- default: 40, higher = better recall, slower query
```

### Batching Embeddings

Membrane generates embeddings synchronously during ingestion. For high throughput:

1. Batch ingests and generate embeddings in parallel
2. Use an embedding cache (e.g., Redis)
3. Pre-generate embeddings and pass them directly (requires API modification)

## Monitoring and Debugging

### Check Embedding Coverage

```sql
SELECT 
    mr.type,
    COUNT(*) AS total_records,
    COUNT(te.record_id) AS embedded_records,
    ROUND(100.0 * COUNT(te.record_id) / COUNT(*), 2) AS coverage_pct
FROM memory_records mr
LEFT JOIN trigger_embeddings te ON mr.id = te.record_id
WHERE mr.type IN ('competence', 'plan_graph')
GROUP BY mr.type;
```

Expected output:

```
    type     | total_records | embedded_records | coverage_pct
-------------+---------------+------------------+--------------
 competence  |           120 |              120 |       100.00
 plan_graph  |            15 |               15 |       100.00
```

### Test Embedding Generation

```go
import "github.com/GustyCube/membrane/pkg/embedding"

client := embedding.NewHTTPClient(
    "https://api.openai.com/v1/embeddings",
    "text-embedding-3-small",
    os.Getenv("MEMBRANE_EMBEDDING_API_KEY"),
    1536,
)

vec, err := client.Embed(ctx, "test query")
if err != nil {
    log.Fatal(err)
}
log.Printf("Embedding dimension: %d", len(vec))  // Should match config
```

### Query Slow Embedding Searches

```sql
EXPLAIN ANALYZE
SELECT record_id
FROM trigger_embeddings
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector
LIMIT 10;
```

Look for `Index Scan using idx_trigger_embeddings_ann`. If you see `Seq Scan`, the index isn't being used.

## Migration and Re-embedding

### Backfill Embeddings for Existing Records

If you enable embeddings after ingesting competence records:

<Steps>
  <Step title="Fetch all competence records without embeddings">
    ```sql
    SELECT mr.id, p.payload_json->>'trigger' AS trigger
    FROM memory_records mr
    JOIN payloads p ON mr.id = p.record_id
    LEFT JOIN trigger_embeddings te ON mr.id = te.record_id
    WHERE mr.type = 'competence'
      AND te.record_id IS NULL;
    ```
  </Step>

  <Step title="Generate embeddings">
    ```go
    embClient := embedding.NewHTTPClient(endpoint, model, apiKey, dims)
    for _, rec := range unembeddedRecords {
        vec, _ := embClient.Embed(ctx, rec.Trigger)
        store.StoreTriggerEmbedding(ctx, rec.ID, vec, model)
    }
    ```
  </Step>
</Steps>

### Change Embedding Model

To switch models (e.g., `ada-002` → `3-small`):

<Steps>
  <Step title="Update config">
    ```yaml
    embedding_model: "text-embedding-3-small"
    embedding_dimensions: 1536  # unchanged
    ```
  </Step>

  <Step title="Truncate old embeddings">
    ```sql
    TRUNCATE trigger_embeddings, embedding_metadata;
    ```
  </Step>

  <Step title="Restart Membrane">
    New embeddings will be generated with the new model on next ingest.
  </Step>
</Steps>

<Warning>
Changing models invalidates all stored embeddings. You must re-embed or accept that old and new records use different embedding spaces (not recommended).
</Warning>

## Troubleshooting

### "embedding request failed with 401"

API key is missing or invalid:

```bash
export MEMBRANE_EMBEDDING_API_KEY="sk-..."
```

### "embedding dimension mismatch"

The config `embedding_dimensions` doesn't match the stored metadata. Reset:

```sql
DELETE FROM embedding_metadata WHERE key = 'dimensions';
```

Or use a fresh database.

### "embedding response did not include an embedding"

The API response format is unexpected. Check the endpoint:

```bash
curl -X POST https://api.openai.com/v1/embeddings \
  -H "Authorization: Bearer $MEMBRANE_EMBEDDING_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "text-embedding-3-small",
    "input": "test"
  }'
```

Expected response:

```json
{
  "data": [
    {
      "embedding": [0.1, 0.2, ...],
      "index": 0
    }
  ],
  "model": "text-embedding-3-small",
  "usage": { "prompt_tokens": 1, "total_tokens": 1 }
}
```

### "Index Scan not used for vector query"

The planner chose sequential scan. Force index use:

```sql
SET enable_seqscan = off;
```

Or rebuild the index with more lists/better parameters.
